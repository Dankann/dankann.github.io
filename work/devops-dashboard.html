One place for everything DevOps

DevOps work on Godforge was spread across Jenkins, a handful of consoles and a chat channel. I built one internal dashboard that fronts all of it: builds, versions, environments, backend state, device performance and requests to the DevOps team. It is the most recent of my Godforge work.

Everything was somewhere else

Answering an ordinary question meant knowing which tool held the answer. Builds and their artifacts were in Jenkins. What was deployed to which environment lived somewhere else. Backend state was a third place. Anything you needed from the DevOps team arrived as a chat message, which is a queue that quietly loses things.

None of those tools were wrong. There were just too many of them, and knowing which one to open was the part that did not scale. Someone new on the project could not answer "what is on staging right now" without finding a person to ask, and the people being asked were the ones with the least time.

One hub instead

The dashboard is a single internal web app that fronts the lot. From it you can browse builds and check one out, see which version is running on which environment, read backend and service state, compare game performance across devices, and file a request to the DevOps team.

That last one matters more than it sounds. The request form files a Jira ticket and posts a Discord notification, so a request starts life as a tracked item instead of a message someone has to remember. Nobody needs to know the right project, the right issue type, or which person to ping.

The cost panel

Build cost tracking existed before the dashboard did. It started as a script somebody ran by hand, then became a daily table the team read. It works better as a panel, because the number now sits next to the builds it came from. "This pipeline got more expensive" and "this pipeline changed last week" are visible on the same screen instead of in two different investigations.

The dashboard also carries AWS Cost Explorer panels for the wider infrastructure spend. The original one-shot script was retired once the panel replaced it, which is the part I care about: the dashboard did not add a place to look, it removed one. The build platform case study covers how that cost tracking came about.

Comparing devices

Performance on a mobile title is a comparison problem. One device's numbers on their own say very little, because the question is always whether this device is worse than it was, or worse than the others. The dashboard puts runs from different devices side by side, which is what makes a regression visible rather than arguable.

Why Node.js on Lambda

An internal dashboard has bursty traffic. It is busy when a build finishes or a release is going out, and idle overnight and at weekends. Keeping a server running and patched for that shape of load is work with no payoff, and most of what the backend does is call other APIs and wait for them.

Running inside AWS also settled the credentials question. Cost Explorer and the build artifacts in S3 already sat behind AWS permissions, so the backend could use IAM roles instead of long-lived keys sitting on a machine somewhere.

Making it worth opening

I also rebuilt the interface: a side navigation so the sections are findable, dark mode, and self-hosted fonts so the dashboard does not need an external font CDN to render. A tool people open all day should not make them hunt, and an internal tool that is unpleasant gets routed around until it may as well not exist.
