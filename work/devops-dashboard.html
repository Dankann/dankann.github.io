One place for everything DevOps

DevOps work on Godforge was spread across Jenkins, a handful of consoles and a chat channel. I built one internal dashboard that fronts all of it: builds, versions, environments, backend state, device performance and requests to the DevOps team. It is the most recent of my Godforge work.

Everything was somewhere else

Answering an ordinary question meant knowing which tool held the answer. Builds and their artifacts were in Jenkins. What was deployed to which environment lived somewhere else. Backend state was a third place. Requests to the DevOps team arrived as chat messages, which are quick to send and easy to lose sight of once the channel moves on.

Each of those tools was a reasonable choice for its own job. What did not scale was the knowledge of which one to open. Someone new to the project could not answer "what is on staging right now" without finding a person to ask, and the people being asked were the ones with the least time to give.

One hub instead

The dashboard is a single internal web app that fronts the lot. From it you can browse builds and check one out, see which version is running on which environment, read backend and service state, see what the team's DevOps services are costing, compare game performance across devices, and file a request to the DevOps team. It reads from the systems that already held those answers rather than keeping its own copy, so there is one place to look and still one source of truth behind each panel.

The request form files a Jira ticket and posts a Discord notification, so a request starts life as a tracked item with a state instead of a message someone has to remember. Nobody needs to know the right project, the right issue type, or which person to ping, and no request depends on a DevOps engineer happening to read the channel at the right moment. It began as a prototype and later took on the studio's identity as it became something people opened every day.

Cost, where the work is

Spend on the DevOps services behind the game was knowable, but only by someone willing to go into the AWS console and work it out, which meant it was not part of anybody's normal day. Decisions that carry a cost, scheduling a nightly job, sizing an environment, keeping a service warm, were being made without the number in front of the person making them.

The dashboard carries that as panels next to everything else. Build cost is one of them, sitting beside the builds it came from, so "this pipeline got more expensive" and "this pipeline changed last week" land on one screen instead of in two separate investigations. AWS Cost Explorer panels cover the wider infrastructure spend around it. Build cost tracking existed before the dashboard as a script somebody ran by hand, and it was retired once the panel replaced it, so this consolidated a place to look rather than adding one. The build platform case study covers how that tracking came about.

Comparing devices

Performance on a mobile title is a comparison problem. One device's numbers alone say very little, because the real question is whether this device is worse than it was, or worse than the others. The dashboard puts runs from different devices side by side, which is what turns a regression into something visible instead of something argued about.

Why Node.js on Lambda

An internal dashboard has bursty traffic. It is busy when a build finishes or a release is going out, and idle overnight and at weekends. Keeping a server running and patched for that shape of load is work with no payoff, and most of what the backend does is call other APIs and wait for them.

Running inside AWS also settled the credentials question. Cost Explorer and the build artifacts in S3 already sat behind AWS permissions, so the backend uses IAM roles instead of long-lived keys living on a machine somewhere. There is no secret to rotate, and no machine whose compromise would hand someone the account.
