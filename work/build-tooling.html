Rewriting the build tool engineers actually use

The Advanced Build Window is how a team of roughly fifty developers and QA on Godforge configures and starts a build without going near Jenkins. I rewrote it from the ground up in Unity's UI Toolkit, on a controller architecture, with presets that hold exact parity to the CI pipeline and a mode that runs the whole game locally.

The tool nobody wanted to touch

The original build window was an IMGUI script that had accumulated years of features. It worked, in the sense that people used it daily and had memorised its quirks. The cost was in the structure: build configuration lived in the UI code, so there was no way to say "build the same thing CI builds," and no way to change the tool without risking every workflow that depended on it.

The most common failure was ordinary. An engineer picks options, hits build, walks away, and comes back twenty minutes later to a failure caused by a setting that was wrong before the first asset compiled. Across a team on a live title, that is a lot of hours spent waiting to be told something obvious.

Separating the tool from its window

The rewrite moved to UI Toolkit and to a controller architecture: build configuration, validation and execution logic live outside the window, and the window renders them. Build logic became testable and callable without an editor window open, and the UI could be changed without breaking someone's workflow.

IMGUI's immediate-mode model encourages mixing state into draw code, which is the coupling the old tool suffered from. Fighting that on every future change would have cost more than the rewrite did.

Presets, and parity with CI

Build configuration became named, reusable presets, and the presets map exactly onto the Jenkins pipeline's own parameters. "It builds locally but fails in CI" is almost always a configuration difference, so sharing the schema makes that difference impossible to express. An engineer reproducing a CI failure picks the preset CI used instead of reconstructing it from memory and a pipeline page.

Two steps instead of one

The build flow splits into PREPARE and BUILD. Prepare does validation and configuration resolution and nothing expensive. Build does the work. Anything knowably wrong up front (a missing platform setting, an unresolvable config, an inconsistent preset) surfaces in seconds, while the engineer is still looking at the screen. Failures show up at the start of a short wait instead of the end of a long one.

Running everything locally

The window also runs the whole thing on the developer's machine. It can start a local game backend and a local Addressables server, so an engineer can build and test end to end without touching the shared dev environment that QA tests against every day. Before that, trying something out meant putting it on the shared environment and risking everyone else's day.

Addressables state is a common source of "it works on my machine" on a Unity project of this size, and it used to be managed by folklore and manual folder deletion. The window exposes the Addressables build cache directly: what is in it, and how to clear it.

Around the tool: merge conflicts

On a Perforce project with a large team, merge conflicts were constant manual work that landed on whoever noticed them first.

I built automated merge-conflict resolution and delivered it in 16 days: automatic checkout, automatic resolve where the resolution is unambiguous, per-user resolution changelists so the remaining decisions land with the person who owns them, and summary reports so nothing resolves silently. It only automates the unambiguous cases. Everything else goes to a human with the context to decide, instead of the bot guessing wrong in someone's stream.

Around the tool: not rebuilding what did not change

A build with no cache takes up to four hours. Even a full cached build takes over an hour. Content changes were triggering those full rebuilds when nothing about them needed one.

I built incremental content-update detection that reconciles Unity's own build reports against source-control changes to decide what actually has to run. If a change does not touch Addressables content, the Addressables build is skipped. If it does not touch client code, the client build is skipped. An incremental build only pays for what the change affects, and that is usually a small fraction of the full run.

Guessing what a content change affects from file paths is a heuristic that eventually ships a broken build. The build report says what Unity actually included, so the pipeline skips work it can prove is unnecessary and runs the full build when it cannot.
