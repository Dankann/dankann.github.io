Rewriting the build tool engineers actually use

The Advanced Build Window is how everyone on Godforge configures and starts a build without going near Jenkins. I rewrote it from the ground up in Unity's UI Toolkit, on a controller architecture, with presets that hold exact parity to the CI pipeline.

The tool nobody wanted to touch

The original build window was an IMGUI script that had accumulated years of features. It worked, in the sense that people used it daily and had memorised its quirks. Its real cost was elsewhere: build configuration lived in the UI code, so there was no way to say "build the same thing CI builds," and no way to change the tool without risking every workflow that depended on it.

The failure mode that hurt most was ordinary. An engineer picks options, hits build, walks away, and comes back twenty minutes later to a failure caused by a setting that was wrong before the first asset compiled. Multiply that across a team on a live title and it is a meaningful amount of the week spent waiting to be told something obvious.

Separating the tool from its window

The rewrite moved to UI Toolkit and, more importantly, to a controller architecture: the build configuration, validation and execution logic live outside the window, and the window renders them. That boundary is what made everything after it possible. Build logic became testable and callable without an editor window open, and the UI became a thing that could be changed without fear.

Choosing UI Toolkit over keeping IMGUI was not about aesthetics. IMGUI's immediate-mode model actively encourages mixing state into draw code, which is exactly the coupling the old tool suffered from. Fighting that on every future change would have cost more than the rewrite.

Presets, and parity with CI

Build configuration became named, reusable presets — and the presets map exactly onto the Jenkins pipeline's own parameters. That parity is the whole point. "It builds locally but fails in CI" is almost always a configuration divergence, and the cheapest way to eliminate a class of bug is to make the divergence impossible to express. An engineer reproducing a CI failure now picks the preset CI used, rather than reconstructing it from memory and a pipeline page.

Two steps instead of one

The build flow splits into PREPARE and BUILD. Prepare does validation and configuration resolution and nothing expensive; build does the work. Everything that can be known to be wrong up front — a missing platform setting, an unresolvable config, an inconsistent preset — surfaces in seconds, at the desk, while the engineer is still looking at the screen.

It is a small structural change and it changed the tool's character. Failures moved from the end of a long wait to the start of a short one.

The Addressables cache tab

Addressables state is the most common source of "it works on my machine" on a Unity project of this size, and until then it was managed by folklore and manual folder deletion. The tool got a dedicated tab exposing the Addressables build cache directly: what is there, and how to clear it. Making the invisible visible removed a recurring support conversation more effectively than any amount of documentation would have.

Around the tool: merge conflicts

Editor tooling is one half of developer experience; the other half is everything that happens before a build is even worth starting. On a Perforce project with a large team, merge conflicts were a standing tax — recurring, manual, and always landing on whoever noticed first.

I built automated merge-conflict resolution and delivered it in 16 days: automatic checkout, automatic resolve where resolution is unambiguous, per-user resolution changelists so the remaining decisions land with the person who owns them, and summary reports so nothing resolves silently. The design principle was narrow on purpose — automate only what is genuinely unambiguous, and route everything else to a human with context, rather than guessing and being confidently wrong in someone's stream.

Around the tool: not rebuilding what did not change

The other tax was full rebuilds triggered by content changes that did not need them. I built incremental content-update detection that reconciles Unity's own build reports against source-control changes to decide whether a full rebuild is actually warranted.

Using the build report as the source of truth mattered. Inferring what a content change affects from file paths is a heuristic that eventually ships a broken build; asking Unity what it actually included is an answer. The pipeline skips the work it can prove is unnecessary and does the full build when it cannot.

The through-line

All three pieces are the same idea applied at different scales: move the moment of failure earlier, and make the state that decides success visible to the person who has to act on it. That is most of what build tooling is.
