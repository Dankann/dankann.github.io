Rewriting the build tool engineers actually use

The Advanced Build Window is how a team of roughly fifty developers and QA on Godforge configures and starts a build without going near Jenkins. I rewrote it from the ground up in Unity's UI Toolkit, on a controller architecture, with presets that hold exact parity to the CI pipeline and a mode that runs the whole game locally.

The tool everybody depended on

The original build window was an IMGUI script that had gained features year after year as the project needed them, and the team used it every day. What it could not do was hold configuration separately from presentation. Build settings lived inside the UI code, so there was no way to say "build the same thing CI builds", and no way to change the window without putting every workflow that depended on it at risk.

The everyday cost was waiting. An engineer picks options, starts a build, walks away, and comes back twenty minutes later to a failure caused by a setting that was already wrong before the first asset compiled. Across a team on a live title, that is a lot of hours spent waiting to be told something that was knowable at the start.

Separating the tool from its window

The rewrite moved to UI Toolkit and to a controller architecture. Build configuration, validation and execution live outside the window, and the window only renders them. That boundary is what made build logic testable, callable with no editor window open, and safe to change, because the interface can move without touching the definition of a build.

Immediate-mode UI invites state to live inside draw code, and every future change to the tool would have paid that coupling again. The rewrite paid it once.

Presets, and one configuration everyone shares

Godforge runs many backend environments, each with its own configs and settings. A developer building locally had no visibility into which of those settings their build was picking up, and no easy way to change them. Two people testing the same feature could be running against different configurations without either of them knowing, and their testing would disagree.

Build configuration became named, reusable presets, which makes the environment an explicit, shared choice on screen instead of an assumption inherited from whatever the machine happened to hold. The presets map onto the Jenkins pipeline's own parameters, so a local build and a CI build are described by one schema rather than two descriptions kept in step by hand.

Everybody tests against the same known configuration, and can say which one it was. "It builds locally but fails in CI" is usually a configuration difference, and a shared schema leaves nowhere for that difference to hide. Reproducing a CI failure is a matter of picking the preset CI used, instead of rebuilding it from memory and a pipeline page.

Two steps instead of one

The build flow splits into PREPARE and BUILD. Prepare does validation and configuration resolution and nothing expensive. Build does the work. Anything knowably wrong up front, a missing platform setting, an unresolvable config, an inconsistent preset, surfaces in seconds while the engineer is still looking at the screen. Failures arrive at the start of a short wait instead of the end of a long one, which turns most bad builds from a lost morning into a correction and a retry.

Running everything locally

Trying something out used to mean putting it on the shared dev environment, the same one QA tests against every day, so an experiment by one engineer could cost several other people an afternoon. The window can start a local game backend and a local Addressables server, so a developer builds and tests the full stack on their own machine and the shared environment stays a place for work that is meant to be seen.

Addressables state is a common source of "it works on my machine" on a Unity project of this size. No tooling existed for it, so the practical fix was deleting the right folder, which meant knowing which one. The window shows the Addressables build cache directly, what is in it and how to clear it, so a developer can resolve their own stale-content problem in seconds without needing that knowledge in the first place.

Around the tool: merge conflicts

On a Perforce project with a large team, keeping streams merged was constant manual work, and it landed on whoever noticed it first rather than on whoever owned the change.

I built automated merge-conflict resolution and had it in production inside three weeks: automatic checkout, automatic resolve where the resolution is unambiguous, per-user resolution changelists, and summary reports so nothing resolves silently. The design point is that automation only touches cases with one correct answer. Everything genuinely ambiguous is routed to the person who wrote the change, with the context to decide, rather than resolved by a guess inside somebody else's stream. The routine merges stopped being anybody's job, and the decisions that need judgement reach the one person able to make them.

Around the tool: not rebuilding what did not change

A build with no cache can take multiple hours. Even a full cached build takes over an hour. Content changes were triggering those full rebuilds when nothing about them needed one.

I built incremental content-update detection that reconciles Unity's own build reports against source-control changes to decide what actually has to run. If a change does not touch Addressables content, the Addressables build is skipped. If it does not touch client code, the client build is skipped. An incremental build pays only for what the change affects, which is usually a small fraction of the full run.

Deciding that from file paths would be a heuristic, and a heuristic that is wrong once ships a broken build. Unity's build report is the authoritative record of what went into the last build, so the pipeline skips only work it can prove is unnecessary and falls back to the full build whenever it cannot. A content change no longer waits on work it could not have affected, and the cases where that is uncertain still get the full run.

How the skip decision is made
  • Unity's build report is the authoritative record of what went into the last build, so it is the input to the decision rather than a guess read off file paths.
  • The pipeline reconciles that report against the changes in source control for the changelist being built.
  • If nothing in the change touches Addressables content, the Addressables build is skipped.
  • If nothing touches client code, the client build is skipped.
  • Anything the reconciliation cannot account for falls back to the full build, so the pipeline only skips work it can prove is unnecessary.
