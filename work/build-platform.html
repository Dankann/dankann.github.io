A build platform for a live F2P game

Godforge is a live free-to-play title at Ironbelly Studios. Over two years I built its build platform from scratch on AWS, moved CI onto it without interrupting releases, and engineered its running costs down with spot capacity, snapshot-backed workspaces and builds that resume where a reclaim killed them.

Where it started

Godforge was already shipping every day, on a build estate that had grown alongside the game. Jenkins ran on bare-metal machines, and none of it existed as code: not the infrastructure, not the build jobs, not the Jenkins configuration itself. Every machine carried years of hand-applied state, so fixing an agent meant working out what made that one machine special, and scaling meant buying hardware and setting it up the same way. Parts of the release path went through Azure Storage Queues and PlayFab CloudScript.

That is the shape most titles reach when the game grows faster than the tooling around it, and it costs more once the game is live, because a broken pipeline is a blocked patch. The job was to give Godforge a build platform that is configurable, reliable and scalable, and that can be rebuilt from code instead of remembered.

Constraints

Two constraints shaped every decision.

  • Releases could not stop. A live game ships on its own cadence, and the migration had to happen underneath a team that kept building all day. There was no maintenance window to negotiate for.
  • Unity builds are not stateless. A build with no cache can take multiple hours, and even a full cached build takes over an hour. Any design that threw away the workspace between builds would buy tidy infrastructure with hours of engineer waiting time.

The platform

Everything is defined in Terraform: VPC and networking, security groups, IAM roles, the EC2 Jenkins controller, and the build agent fleet. One description of the platform lives in source control, and applying it is how the platform changes.

Unity agents keep their workspaces on EBS volumes that outlive the instance. When an agent starts a job it selects a workspace volume dynamically, attaches it, and builds against warm state. When the job ends the volume is detached and returned to the pool. The selection logic assumes the cloud can always surprise it, so it is written to self-heal: it reconciles what AWS says is attached against what the fleet believes, recovers a partial attachment in place, and sweeps orphaned volumes left behind by instances that died mid-build. Failures there are rare; the point is that nobody has to notice one for the fleet to recover.

The fleet stays disposable without making builds slow. An instance can be replaced at any time, and the workspace it was building in is kept, so recovering from a dead agent costs a retry instead of a cold build.

The volume lifecycle in detail
  • An agent picking up a job selects a free workspace volume from the pool, attaches it, and builds against whatever state the previous job on that volume left behind.
  • The fleet never trusts its own record of what is mounted. It reconciles against what AWS reports before it acts, so a stale record cannot strand a volume.
  • A partial attachment is recovered in place rather than abandoned, so a half-attached volume does not cost the job a cold build.
  • Volumes orphaned by instances that died mid-build are swept and returned to the pool, so a dead agent does not quietly remove capacity from the fleet.
  • Because the workspace outlives the instance, replacing an agent costs a retry instead of a build from cold. That is what makes a spot fleet usable for Unity builds at all.

Capacity stopped being a purchasing decision. Agents run as spot instances in a scaling group, so when the team needs more builds running at once, the group brings up another instance. Bare metal handles a fixed number of builds at a time, and that number only moves when someone buys a machine. Storage works the same way. If the project grows in asset size, the volumes grow with a Terraform change, where on bare metal it means requesting a new machine or physically installing SSDs. Growth in team size or asset size is now a change to a file rather than a lead time.

Pipelines on top

On top of that sits the Jenkins estate I own end to end: multi-platform Unity build pipelines covering Android, iOS, Windows and macOS, game-config and Addressables builds, and orchestrator and retention pipelines that decide what runs and which old builds and workspaces get cleaned up. Four platforms come out of one pipeline codebase, not four that drifted apart.

A Unity build log runs to tens of thousands of lines, and the line that explains the failure is rarely near the end, so reading one was a skill the team did not have a reason to acquire. The pipelines parse the log and extract the errors that caused the failure, in priority order, onto the build page. A developer sees why their build broke without opening a log or asking DevOps to read it for them.

I also rebuilt the artifact upload path that used to fail intermittently under load; uploads now run to completion without anyone watching them.

Migrating without stopping

Moving CI onto the new environment ran underneath a team that kept building all day; there was no freeze to hide behind. Rather than run a second set of pipelines for the new fleet, I unified the pipeline codebase so the same definitions cover both the AWS agents and the machines that stayed bare metal, moved pipelines across one at a time, and deleted nothing until the new path had run enough real builds to be trusted. The team shipped through the cutover without losing a release.

When the game's backend later moved from Azure to Metaplay, the platform's share of that was deliberately small: the Azure deployment pipeline was retired and a Metaplay one took its place, and the old path kept working right up to the cutover.

Running it cheap

A cloud build platform is a bill somebody pays, so cost was engineered like any other requirement. The agents run on spot instances instead of dedicated ones, which is only cheap if you respect how spot behaves: AWS can reclaim an instance mid-build, and a naive pipeline that retries from scratch throws away hours of build time every time it happens. Retry that way often enough and spot costs more than the dedicated capacity it was supposed to undercut. Our pipelines resume from the step that was running when the reclaim hit, so a reclaimed instance costs minutes, not a build.

Storage got the same treatment. Workspace-sized EBS volumes are expensive, so only the busiest pipelines keep persistent volumes. Everything sporadic, including developer test builds, restores its workspace from snapshots instead, which trades a little startup time on rare builds for not paying for idle disks. What a build costs still lands where the builds are, on the team's ops dashboard.

What it added up to

The platform is described in Terraform, the pipelines live in one codebase that ships four platforms, and what a build costs is on a dashboard anyone can open. Roughly fifty developers and QA build on it every day, the migration never cost them a release, and growing the platform is a change someone can review rather than hardware someone has to order.
