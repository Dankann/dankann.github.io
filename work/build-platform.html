A build platform for a live F2P game

Godforge is a live free-to-play title at Ironbelly Studios. Over two years I built its build platform from scratch on AWS, ran two migrations without interrupting releases, and added cost tracking so the team can see what a build costs.

Where it started

The build estate I inherited was split across platforms and held together by convention. Jenkins ran on bare-metal machines. Parts of the release path went through Azure Storage Queues and PlayFab CloudScript. Agent machines carried state nobody could reproduce. When a build broke, the honest answer to "why" was usually "log into the machine and look."

None of that is unusual for a title that grew fast, but it hurts more when the game is live, because a broken pipeline is a blocked patch. The job was to give Godforge a build platform that could be reasoned about, reproduced, and handed to somebody else.

Constraints

Three things shaped every decision.

  • Releases could not stop. A live game ships on its own cadence, and the migration had to happen underneath a team that kept building all day. There was no maintenance window to negotiate for.
  • Unity builds are not stateless. A cold Unity project import and Addressables build costs tens of minutes. Any design that threw away the workspace between builds would buy tidy infrastructure with hours of engineer waiting time.
  • I would not be the only operator forever. Anything that only worked because I knew a trick was a liability. That pushed the platform toward Terraform and toward pipelines that explain their own failures.

The platform

Everything is defined in Terraform: VPC and networking, security groups, IAM roles, the EC2 Jenkins controller, and the build agent fleet. The part worth explaining is what the agents do with their disks.

Unity agents keep their workspaces on EBS volumes that outlive the instance. When an agent starts a job it selects a workspace volume dynamically, attaches it, and builds against warm state. When the job ends the volume is detached and returned to the pool. Attach and detach are the two operations most likely to fail halfway, so the selection logic is self-healing: it reconciles what AWS says is attached against what the fleet believes, recovers from partial attachments, and sweeps orphaned volumes left behind by instances that died mid-build.

That is what lets the fleet stay disposable without making builds slow. Instances can be replaced at any time. The workspaces they mount are kept.

Pipelines on top

On top of that sits the Jenkins estate I own end to end: multi-platform Unity build pipelines across Android, iOS and macOS, game-config and Addressables builds, and orchestrator and retention pipelines that decide what runs and what gets cleaned up.

Two pieces mattered more than their size suggests. The first is log parsing with prioritised error extraction. A Unity build log is tens of thousands of lines and the line that matters is rarely near the end, so the pipeline surfaces the actual failure instead of the last stack trace. The second is artifact upload, which started as a shell script, became Python, and ended as parallel Jenkins stages with tuned concurrency. Uploads had been failing intermittently under load for long enough that people had learned to just retry. After the rewrite that failure stopped happening.

Migrating without stopping

Two migrations ran on this platform. The first moved CI onto the new AWS environment, on a unified pipeline codebase covering both the AWS fleet and the machines that stayed bare metal, so there was one set of pipeline definitions instead of two dialects that had drifted apart. The second moved the game's build and release pipelines from Azure to a Metaplay backend, which meant a PlayFab CloudScript bypass and reliability fixes to the Azure Storage Queue handling that had to keep working right up to the cutover.

Neither migration got a freeze. The approach was the boring one: make the new path work in parallel, move one pipeline at a time, keep the old path reversible until the new one had run enough real builds to be trusted, and delete only afterwards. The team kept shipping through both cutovers. I also wrote the post-cutover operational guide the team still runs on, so the platform does not depend on me being around.

Then, the cost

Nobody could say what a single build cost, so nobody could argue about whether it was worth it.

It started as a one-shot script, then became a daily table the team actually read, then a live panel in an internal ops dashboard I built on Node.js and AWS Lambda. The original script was retired once the panel replaced it. The dashboard also carries AWS Cost Explorer panels and a self-service request flow that files a Jira ticket and posts a Discord notification, so infrastructure requests stop arriving as direct messages that get lost.

What it added up to

Over 2,000 submitted changes in 18 months, across build infrastructure, pipelines and backend migration. The platform is in Terraform, the pipelines are in one codebase, and what a build costs is on a dashboard anyone on the team can open.
