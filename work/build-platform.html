A build platform for a live F2P game

Godforge is a live free-to-play title at Ironbelly Studios. Over two years I built its build platform from scratch on AWS, ran two migrations without interrupting releases, and added cost tracking so the team can see what a build costs.

Where it started

Godforge was already shipping every day, on a build estate that had grown alongside the game. Jenkins ran on bare-metal machines. Parts of the release path went through Azure Storage Queues and PlayFab CloudScript. Agent machines carried state that had accumulated over years of use rather than being described anywhere, so working out why a build failed usually started by connecting to the machine that ran it.

That is the shape most titles reach when the game grows faster than the tooling around it, and it costs more once the game is live, because a broken pipeline is a blocked patch. The job was to give Godforge a build platform that could be reasoned about, reproduced, and handed to somebody else.

Constraints

Three things shaped every decision.

  • Releases could not stop. A live game ships on its own cadence, and the migration had to happen underneath a team that kept building all day. There was no maintenance window to negotiate for.
  • Unity builds are not stateless. A build with no cache can take multiple hours, and even a full cached build takes over an hour. Any design that threw away the workspace between builds would buy tidy infrastructure with hours of engineer waiting time.
  • The platform would outlive my time as its only operator. Anything that depended on one person's knowledge to run was a risk, so the design leaned on Terraform and on pipelines that explain their own failures.

The platform

Everything is defined in Terraform: VPC and networking, security groups, IAM roles, the EC2 Jenkins controller, and the build agent fleet. One description of the platform lives in source control, and applying it is how the platform changes.

Unity agents keep their workspaces on EBS volumes that outlive the instance. When an agent starts a job it selects a workspace volume dynamically, attaches it, and builds against warm state. When the job ends the volume is detached and returned to the pool. Attach and detach are the two operations most likely to fail halfway, so the selection logic is self-healing: it reconciles what AWS says is attached against what the fleet believes, recovers from partial attachments, and sweeps orphaned volumes left behind by instances that died mid-build.

The fleet stays disposable without making builds slow. An instance can be replaced at any time, and the workspace it was building in is kept, so recovering from a dead agent costs a retry instead of a cold build.

Capacity stopped being a purchasing decision. Agents run as spot instances in a scaling group, so when the team needs more builds running at once, the group brings up another instance. Bare metal handles a fixed number of builds at a time, and that number only moves when someone buys a machine. Storage works the same way. If the project grows in asset size, the volumes grow with a Terraform change, where on bare metal it means requesting a new machine or physically installing SSDs. Growth in team size or asset size is now a change to a file rather than a lead time.

Pipelines on top

On top of that sits the Jenkins estate I own end to end: multi-platform Unity build pipelines covering Android, iOS, Windows and macOS, game-config and Addressables builds, and orchestrator and retention pipelines that decide what runs and what gets cleaned up. Four platforms come out of one pipeline codebase, not four that drifted apart.

A Unity build log runs to tens of thousands of lines, and the line that explains the failure is rarely near the end, so reading one was a skill the team did not have a reason to acquire. The pipelines parse the log and extract the errors that caused the failure, in priority order, onto the build page. A developer sees why their build broke without opening a log or asking DevOps to read it for them.

Artifact uploads were the other daily cost. They failed intermittently under load often enough that people had learned to just retry, which put a manual step in front of every release that hit a bad moment. Rebuilding the upload path stopped that failure. Uploads run to completion on their own, and nobody watches them any more.

Migrating without stopping

Two migrations ran on this platform. The first moved CI onto the new AWS environment. Rather than run a second set of pipelines for the new fleet, I unified the pipeline codebase so the same definitions cover both the AWS agents and the machines that stayed bare metal. One codebase means a fix lands once for every platform instead of being copied into a second set and slowly falling out of step. The second migration moved the game's build and release pipelines from Azure to a Metaplay backend, which meant a PlayFab CloudScript bypass and reliability fixes to the Azure Storage Queue handling, since the old path had to keep working right up to the cutover.

Neither migration got a freeze, so both were designed to stay reversible. The new path ran in parallel with the old one, pipelines moved across one at a time, and nothing was deleted until the replacement had run enough real builds to be trusted. Every step could be undone on the day it was taken, which is what let the work happen underneath a team that kept building all day. The team shipped through both cutovers without losing a release. I also wrote the post-cutover operational guide the team still runs on, so day-to-day operation of the platform does not depend on me.

Then, the cost

Running builds in the cloud turns machine time into a line on a bill, and nobody could say what a single build contributed to it. Without that number, questions like whether a nightly job earns its schedule, or whether a pipeline change made things more expensive, had no answer anyone could check.

I built per-build cost tracking and put it where the builds already are, as a live panel in an internal ops dashboard on Node.js and AWS Lambda. Cost became something a lead can look up in the same place they look up the build, instead of a question that needed someone to go and work it out. That dashboard grew into the team's single place for everything DevOps, and cost is one part of it.

What it added up to

The platform is described in Terraform, the pipelines live in one codebase that ships four platforms, and what a build costs is on a dashboard anyone can open. Roughly fifty developers and QA build on it every day, neither migration cost them a release, and growing the platform is now a change someone can review rather than hardware someone has to order.
